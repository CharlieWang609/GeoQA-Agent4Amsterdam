Compose the concrete workflow as an ordered dataflow of steps, each applying one of the supplied allow-listed operations by its algorithm_id. Each operation lists a description, its parameters (with allowed values and defaults) and its outputs; choose operations by what the task needs. Give every step a unique step_id and every output a fresh ref. Bind data-binding parameters with source "ref" to the binding refs or to earlier steps' output refs; bind scalar configuration as "literal" values respecting each parameter's allowed_values, and omit optional parameters you do not need rather than binding them to null or the string "None"; bind time-dependent text as "template" strings whose placeholders come only from the supplied template_placeholders (for example "{supports_retrieved_at}"). A data-binding parameter that lists geometry kinds (point, line, polygon) accepts only refs carrying such geometry: a bound layer's kind follows its geometry_types, geopandas:centroids yields points, and geopandas:buffer and geopandas:overlay yield polygons. The goal's aggregation and value_attribute must be realised literally: a sum, mean, min or max of a source attribute means a step whose statistic is that aggregation over that attribute (countpointsinpolygon with statistic and value_field, or aggregate with statistic and field), never a count of records. Each bound layer lists its attributes with their measurement_scale: sum and mean statistics need a numeric column, while a count of objects needs no value column. Declare final_output_ref, result_table_ref, and diagnostic_refs so the outputs satisfy the supplied output_contract, including its exact column names: when an operation's native output columns differ, add steps such as geopandas:renamefield until the declared result table carries exactly the contract columns (geopandas:sjoinnearest can name its distance column directly via distance_field, and prefix controls the names of copied fields). A data-binding parameter's data_kind says whether it takes vector features or a raster: raster refs (a bound layer with data_kind raster, or a rasterio:* output) are consumed only by rasterio operations, and a raster chain must end in rasterio:zonalstatistics (one value per vector zone) or rasterio:samplepoints (one value per vector point) so the answer is a keyed vector table. Every period in the Task Specification must reach the plan as literals: its start and end dates are the start_date and end_date of gee:filter. An Earth Engine image collection (data_kind image_collection) is remote: gee:filter narrows it to a date range and cloud limit, gee:composite turns it into one image (data_kind image), gee:bandmath derives a band such as NDVI from that image, and gee:reduceregions (a value per vector zone) or gee:export (a local raster for rasterio operations) is the only way its result leaves the cloud; a collection cannot be reduced without a composite. A raster band whose measurement_scale is nominal (class codes) must be turned numeric with rasterio:bandmath (for example landcover == 10, which yields 1 inside the class and 0 elsewhere, so its zonal mean is the class fraction) before any statistic is taken. Every retained ref (the final output, the result table, the diagnostics) must be a sink output. Deterministic validation checks the operation contracts, the dataflow, the columns each step names and the output contract after generation, and blocks any workflow that fails.

In geopandas:calculatefield expressions the pseudo-columns _area and _length carry the geometry measurements in CRS units (EPSG:28992 = metres).
